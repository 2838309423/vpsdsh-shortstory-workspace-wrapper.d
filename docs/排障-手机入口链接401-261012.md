- 现场主机：`usavps`（Tailscale `100.85.190.17`）

## 二、根因（读 `@deepseek-ai/dsh-client-connection` 源码所得）

- `BrowserAuth` 两把钥匙：
  1. **launch token**：进程启动时 `randomBytes(32)` 生成，只活在内存里（`WeakMap`）⇒ **每次启动都换**，
     `/ ?token=` 是唯一换 cookie 的入口；
  2. **cookie 签名密钥**：持久化在 `~/.dsh/.credentials.yaml`（`client-connection/browser-session`，本机 2026-10-08 建后未变）
     ⇒ **cookie 能扛重启，令牌不能**。
- cookie 名绑定 authority（`dsh-auth-<sha256(host:port)>`）⇒ 换域名/换端口访问等于没 cookie。
- cookie 寿命默认 `cookieMaxAgeDays: 30`（`z.natural().min(1).default(30)`）。
- ⇒ 手机端只要丢过 cookie（手机浏览器清数据、隐私模式、iOS ITP 之类），旧令牌链接就只剩 401；
  而它丢 cookie 的时间点与「2026-10-10 12:30 那次重启换令牌」一叠加，就表现为「以前能开、现在打不开」。

## 三、本次处置

1. **给甲方当前令牌链接**（`bash bin/web.sh url` 取，本次 = `http://100.85.190.17:19387/?token=bQK8…`）：
   手机开一次即换到 cookie，之后连干净 URL `http://100.85.190.17:19387/` 也能进。
2. **补 `bin/web.sh ensure` 的坑**：`@reboot` 与 2 分钟看门狗走的都是 `ensure`，而它原来只拉会话、
   **不刷新 `state/url.txt`** ⇒ 重启后文件里留着上一代的死令牌，照着发出去的链接必然 401。
   现在 `ensure` 结束前顺手 `refresh_url`（只读日志尾，幂等、便宜；实测两个会话不被重启，令牌不变）。
3. **把会话 cookie 寿命从 30 天调到 10 年**（`profile/cordis.patch.yml` 新增 `connection` 条目，
   已 `bash bin/apply-profile.sh --force` 落地）：**每台设备认证一次就长期有效**，不再受重启影响。
   实测坑：用户 patch 层按 id **整条替换** config —— 只写 `cookieMaxAgeDays` 会把
   `trustedHosts: !!js ctx.webRuntime.trustedHosts` 冲掉（手机侧 `/api` 信任栅栏失守、SPA 打不开），
   所以必须把 `trustedHosts` 原样抄回来；已用 `dsh --profile vps --dump-config` 验证组合结果两条都在。
   ⚠ **本项要重启 web 才生效**，而重启会掐掉当前正在说话的浏览器会话（本次没重启）。
