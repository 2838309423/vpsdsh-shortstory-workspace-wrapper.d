# 落地记录：会话轮转插件装到 usavps 的 DSH（2026-10-13）

> 母题：把甲方桌面端开发并长期在用的 `@local/dsh-session-rotation.d`（会话轮转）**装到 usavps 上那套
> DSH**（文本服务实例，profile `vps`，`@deepseek-ai/dsh@0.2.0-rc.2`）。
> 本文是这次装机的**唯一真值**：装机面、验收读数、顺手修的两个真缺陷、服务器上做不到的边界、开闸与回滚。

## 一、结论（一句话）

- **装上了，跑的是出厂档 `mode=observe`（只报不改）**：插件在每个 `agent/pre-step` 读 L2 token 与
  transcript 字节，按阈值往 `state/rotation/plugin.log` + `state/rotation/audit/dsh-rotation.jsonl`
  写具名记录；**不建会话、不归档、不移文件**。
- **顺带修了一个停摆一整天的静默缺陷**：2026-10-12 插件仓从 `$HOME/<包名>` 搬进 `$HOME/dsh.d/` 时，
  `profiles/vps/node_modules/@local/*` 两条软链没跟着改 ⇒ **此后任何一次重启都会静默丢掉
  statusline + copy-path**（DSH 只打一行 `dsh: skipping profile bundle …`，不报错、不退出）。
  本次已修（链子重建 + `apply-profile.sh` 里改根 + 记进 AGENTS.md）。
- 服务器上**只能 observe**：真跑链条的两条腿（REAP 脚本路径、跨会话 headless 驱动）都是 Windows 写的，
  见 §五。

## 四、顺手修的两个真缺陷

### 4.1 profile 软链悬空（**本次装机的前置阻塞项**）

- 事实：2026-10-12 插件仓从 `$HOME/dsh-statusline.d`、`$HOME/dsh-copy-path.d` 搬进 `$HOME/dsh.d/`
  （没有任何单据记这笔），但 `bin/apply-profile.sh` 里写死的链接目标与 profile 的 `link:` 登记**都没改**
  ⇒ 活 profile 里两条链子指向已不存在的路径。
- 为什么一直没人发现：DSH **不硬失败**——启动只打一行
  `dsh: skipping profile bundle "@local/dsh-statusline.d": … cannot resolve …` 然后继续启动；
  而活着的 DSH 进程是 2026-10-10 12:30 起的，模块早解析完了 ⇒ 只有**下一次重启**才会暴露。
- 取证（隔离冷启实测，2026-10-13）：`dump-config` 与真启动都打出两条 `skipping`；
  `--port 19499` 的隔离实例照样起得来 ⇒ 症状就是"重启后状态栏和复制路径插件**悄悄没了**"。
- 修法：`apply-profile.sh` 引入 `PLUGIN_ROOT="${DSH_PLUGIN_ROOT:-$HOME/dsh.d}"`，三条链子都按它建；
  profile 的 `link:` 登记同步改成 `~/dsh.d/…`。判据：`ls -l ~/.dsh/profiles/vps/node_modules/@local/`
  三条都是 `OK`（不是 `DANGLING`），重启后 `web.log` 无 `skipping`。

### 4.2 插件的 `logLine` 会吞掉首启两行（上游已修，commit `c983979`）

- 事实：`logLine()` 里 `appendFileSync(LOAD_LOG, …)` 外面只有 `try/catch`，**不建目录**。
  当 `DSH_SESSION_ROTATION_LOG` 指向一个还不存在的目录时，前两行
  `host half v0/v1 loaded`（**装机判据就是这行**）以 ENOENT 被吞掉；要等
  `writeAudit()` 的 `mkdirSync` 把目录建出来，后面的行才恢复。
- 为什么桌面端从没暴露：缺省 `.load.log` 就在插件目录里，目录必然存在；只有自定义 LOG 路径（服务器侧）才必现。
- 修法：`logLine` 自己 `mkdirSync(dirname(LOAD_LOG), { recursive: true })`（一行，幂等），
  四支自测全绿后 push 到 gitee，服务器侧 `git pull --ff-only` 到 `c983979`。

## 五、服务器上做不到的（要真轮转必须先解决的边界）

1. **REAP 腿**：`index.js` 里 `REAP_SCRIPT` **写死** `D:\dsk-workspace.d\usavps-bridge.d\bin\dsh-session-reap.py`；
   `DSH_SESSION_ROTATION_PYTHON` 只能换解释器、换不了脚本路径 ⇒ 服务器上跑到 REAP 一步必然读不到脚本。
   （挡在 `reap=apply` 后面；出厂 `reap=dry`，observe 档根本走不到。）
2. **跨会话接续腿**：`driver` 的对面是 **Windows 侧** headless 驱动（Chrome/CDP + `schtasks` 唤醒 +
   `hb-run.ps1`），服务器上没有这套 ⇒ 保持 `driver.enabled=false`，本机不导出任何 `DSH_SESSION_ROTATION_DRIVER_*`
   （不导出 ⇒ 更不会去碰 `C:\…\headless-driver`）。
3. 因此本机**只装 observe**。要把轮转真跑起来，得先把这两条腿 Linux 化（给 REAP 脚本路径加 env 开关 +
   一个 Linux 版交接机制），那是另一件工程，不在本次范围。

## 七、踩坑（给下一个装机的人，三条都是本次实测）

1. **搬插件仓以后必须跑 `apply-profile.sh` 重建链子**，并检查 `DANGLING`。DSH 对解析失败是"静默跳过"，
   不会让服务起不来——最坏情况下你以为装好了，其实少了插件。
2. **env 只在启动时读，而且父 shell 会盖掉默认值**：我在同一个 shell 里先 `source` 了**旧版**
   `bin/env.sh`（把旧的 `DSH_SESSION_ROTATION_STATE` export 进了环境），随后在那个 shell 里
   `bash bin/web.sh restart` ⇒ 子进程继承了旧值，`${VAR:-default}` 的新默认值**不生效**，
   日志里配置件落点还是旧位置。**教训**：验证脚本别在同一 shell 里"先 source 再起服务"，
   重启前 `unset` 这批变量；判据要看 `/proc/<pid>/environ`，别只看文件。
3. **`DSH_SESSION_ROTATION_STATE` 是"指针文件"的路径不是目录**（插件对它的 `dirname()` 才是
   `rotation-config.json`/首跑闸的落点）。给目录 ⇒ 配置文件被甩到上一级；不给 ⇒ 多一层 `state/` 套娃。
   两种我都实测踩到过，正确值见 §二。
4. **不带上这批 env 跑 DSH，插件会照 Windows 缺省路径在 cwd 下落盘**：任何一次
   `dsh --profile vps …`（我这次是**只想看组合树的 `--dump-config`**，它也会真 mount 一遍插件）如果
   没设 `DSH_SESSION_ROTATION_INBOX` / `_AUDIT`，就会在**当前目录**里建出
   名字叫 `D:\dsk-workspace.d\usavps-bridge.d\audit\dsh-rotation.jsonl` 的**单个文件**（Linux 下
   反斜杠是合法文件名字符，所以不是目录树）——我这一趟就把这个怪件跟着提交进了包装仓，
   随后 `39e39a4` 清掉。**教训**：在仓里跑任何 DSH 命令前先确认这 6 个 env 在；看到形如 `D:*`
   的未跟踪件，那不是"插件坏了"，就是这条缺省路径露头。
